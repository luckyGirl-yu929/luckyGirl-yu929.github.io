01

业务痛点与产品方案

在硬件研发与测试中，经验通常分散在个人记忆、历史报告、Bug 记录与跨部门沟通里。以下四个痛点来自我在汽车电子 Tier 1 的实际观察，每一条都对应产品中的一个具体环节。

痛点 01

老工程师缺乏沉淀动力

测试和调试本身已占满工时，额外整理文档既耽误工作又没有工时——经验停留在口头交流中，甚至「经验跟着人走」。

产品方案 · 入口 C口述即可，不必从零写文档。AI 分类与字段提取、按模板生成草稿，工程师只做确认与补充。
痛点 02

资料分散且格式不统一

测试方法记在测试报告里，仪器操作写在操作文档里，Bug 过程留在问题日志或聊天记录里——难以形成完整、可检索的经验记录。

产品方案 · 统一模板测试方法卡与 Bug 经验卡两套统一模板。原始输入逐句保留，AI 整理结果与原始材料都可回溯核对。
痛点 03

跨项目经验难以复用

即使其他项目解决过类似问题，新人也不知道资料在哪、该找谁，且非项目组人员通常没有访问权限。

产品方案 · 权限内共享共享的是测试与排查经验，而非受限文档。沿用企业安全规则（如受控文档 SI-002），项目机密不进入检索范围。
痛点 04

新人不会提问，也难以检索

新人只知道「测试结果异常」，不知道如何检索、提问时该提供什么信息；向老工程师提问也问不到点子上。

产品方案 · Query 改写AI 先追问 1–3 个关键问题，再改写检索条件。把模糊口语转化为有上下文、有边界、可检索的结构化 Query。

三级状态，严格区分：① 草稿（未确认，不写入）；② 工程师确认后 --commit 写入，记录 review_status=待审核；③ 评审通过后才成为正式知识。待审核内容在检索中只作「待确认线索」，不作正式操作依据。

检索口径（如实描述）：当前实现为关键词 + 别名扩展 + 字段过滤 + 排序的可解释检索，读取 knowledge-base.json；未引入向量检索。规模扩大后可升级，但任何升级不得改变「结果带来源与状态」的契约。

语音输入（平台能力衔接）：本 Skill 脚本不含语音识别。若提供音频，先由平台语音转文字能力转写为文本，再走入口 C 同一流程；转写内容同样先生成草稿待确认。

写入纪律：沉淀只新增文件不覆盖已有知识；--commit 必须发生在工程师看过草稿并确认之后；写入后自动重建索引并复核新记录可被检索。

06

AI 能力边界与风险控制

风险高度集中在「AI 输出看起来对」。设计原则：AI 多做事，人做判断，每一条 AI 输出可追溯、可回退、可溯源。

AI 可以

  • 整理口述经验，生成结构化知识卡草稿
  • 补充检索上下文，改写模糊问题为可检索 Query
  • 查找相关知识：相似案例、测试方法、关联知识卡
  • 生成结构化测试清单和 Bug 经验草稿
  • 展示每条结果的来源、审核状态与适用限制

AI 不能直接决定

  • 未经确认的测试标准和电气限值（以器件手册为准）
  • 最终 Pass / Fail 判定（属合规与数值判定）
  • 没有证据支撑的故障根因（只列「嫌疑待验证」）
  • 正式规范发布和变更放行（待审核 ≠ 已发布）

核心原则：AI 负责整理、检索和辅助解释；工程师负责专业判断与审核；知识库负责管理经过确认的经验。器件规格、产品需求、公司测试规范和实际测试结果必须明确区分，不能混为一谈。

07

项目总结与后续方向

解决的核心问题

  • 经验难沉淀：口述即可生成草稿，降低整理成本
  • 知识难检索：Query 改写 + 别名扩展，模糊问题也能查
  • 新人难上手：带来源与状态的方法卡 / 排查路径

产品思路

  • 将知识沉淀、知识检索与人工审核整合为闭环
  • 两个方向共享一套知识库与数据结构
  • 新经验回流沉淀流程，知识持续更新

当前成果

  • 基于 WorkBuddy 搭建 Skill MVP（23 条初始知识）
  • 以三个场景验证全链路：沉淀 / 查询 / 排查
  • 产出 TM-016、DVT 清单、BE-007 草稿三份真实交付物

后续优化方向

  • 完善测试集与检索质量评估
  • 知识版本管理与权限控制
  • 沉淀-复用的效果量化（不预设数字）

回顾这个项目

AI 是能力放大器，而不是决策替代者。真正有价值的 AI 产品，需要理解用户场景，找到 AI 能力与业务流程之间的结合点。

TM-016 · 以太网接口断电插拔操作规范

摘要

一次已实际发生的器件损坏（PHY 芯片引脚真损坏，工程师本人经历），核心价值是一条可执行的操作顺序规范：进行任何网线 / 以太网跳线 / 转接板的插拔前，必须先将相关设备全部断电。它不是芯片功能测试方法，也不是根因分析报告。

关键流程

步骤内容
全部断电主设备 → 被测板（含转接板）→ 确认指示灯熄灭、输出电压归零
断电插线断电状态下插好网线与转接板，接头插到位
复核连接线缆无破损 / 无裸铜 / 无短路，网口触点无异物
依次上电上电顺序属项目定义项，按项目规范执行（待确认）
通电后只允许拔插非电气侧；禁止触碰 RJ45 金属触点、禁止反复带电插拔试错

状态与限制

待审核 工程师经验 · 已发生事故

本条不含任何电压 / 电流 / 阻抗限值，PHY 耐压与引脚绝对最大额定值必须以器件手册为准；依据来源（项目 EHS 规程 / 安全规范）待补充。在依据补齐前，按「工程师经验 + 一次实证事故」支撑，不作为公司正式规范引用。

WorkBuddy 实测截图（点击放大）

① 口述输入千兆以太网带电插拔险些烧毁的原始经验
② 确认后写入澄清三处细节后生成规范卡，标注待审核
③ 缺失字段未确认前不写入，待补项一目了然
④ 草稿预览分类判定 + 结构化草稿，原文逐句保留

DVT · 以太网链路测试检查清单（摄像头 / PHY 转接板）

摘要

由知识库 TM-010《通信与高速数据链路测试》S5 以太网步骤 + TM-016《以太网接口断电插拔操作规范》整合而成。适用范围：摄像头产品的以太网 PHY 转接板（半成品板级验证），目标仅验证「链路通不通」（link-up / 协商 / 连通性 / 丢包），不含吞吐 / 延迟性能与协议一致性。阶段：DVT。

检查步骤

步骤检查内容
S0 安全检查两侧设备全部断电 → 断电插线 → 复核（最优先，跳过不得进入后续）
S1 上电与链路建立按项目顺序上电；读 PHY 状态寄存器确认 link-up（寄存器地址依手册，待确认）
S2 协商结果核对协商速率（100M/1000M）与双工是否符合项目预期
S3 连通性与丢包互 ping 统计丢包率与延迟分布；抓包确认无异常错帧 / CRC 错误
S4 DVT 增强项样本量 ≥3 台、高低温复测、线缆变量、长时稳定性、插拔循环（每次回 S0）

待确认项（工程师补全后才可放行）

PHY 芯片型号 / 位号 / 板卡版本、端口是否带 PoE / 是否声明热插拔、上电顺序（项目规范）、PHY 状态与协商寄存器地址、丢包阈值与 ping 包数、DVT 样本量与温度范围、链路伙伴型号。清单中的具体器件信息、测试参数和判定阈值，仍有需要工程师确认的项目。

BE-007 · PMIC 上电异常故障经验草稿

摘要

车载摄像头整机样机，上电瞬间指示灯闪一下就灭（不是完全不亮），供电经过 PMIC 转接板；上位机串口助手报 Error 0x0A（含义待确认，疑似设备无响应 / 通信失败，属于结果而非根因）。本卡片由工程师口述整理生成，根因尚未定位，证据待补充，草稿待审核。

分层排查路径（供电 → 时序 → 链路）

层级动作
① 验证测量链仪器共地、探头接地弹簧 <1cm、电源先设限流再升压，排除假故障
② 供电检查冷态量 PMIC 各输出轨对地阻抗，判断短路 / 低阻（OCP/SCP 关断为强嫌疑，待确认）
③ 上电波形与时序多通道示波器以输入 / 第一级轨 / EN / PGOOD 触发，锁存完整上电过程
④ 通信链路0x0A 作为通信失败结果，不优先排查串口，先解决供电

所需仪器与待确认项

仪器：示波器（多通道，抓上电波形最关键）、万用表、可编程电源（限流 + 看输入跌落）、电子负载（可选，验证带载跌落）。

待补充：PMIC 具体型号、当前阶段（EVT/DVT/PVT）、哪颗 LED / 哪路供电、0x0A 出自哪个软件、实测阻抗与波形结果、复现条件。排查假设不写成已确认根因，不编造测试限值。

② 分层排查先供电后通信，不猜测错误码含义
