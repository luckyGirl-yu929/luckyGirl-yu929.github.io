从真实工程痛点出发，
重新设计实验室预约体验。

在汽车电子 Tier 1 供应商担任电子工程师期间，我从实验室硬件搭建逐步接触到车载摄像头与雷达测试，也发现测试之外的资源协调同样耗时：跨部门找设备、逐项预约、等待审批。

因此，我设计了 LabOps Agent 原型：探索让工程师描述测试任务，由系统辅助推荐资源、校验预约规则，并在人工确认后完成提交与状态追踪。

01

起点：从实验室搭建，到发现预约流程中的问题

刚进入汽车电子行业时，我作为电子工程师参与实验室硬件搭建，开始了解测试台、仪器设备与实验环境。之后在车载摄像头和雷达相关测试工作中，我逐渐接触到设备使用与跨部门借用的实际流程。

当一项测试需要多台仪器配合时，工程师不仅要明确测试方案，还要自行查找所需设备、逐项核对空闲时间并提交预约；部分跨部门设备还需要等待管理员审批。如果其中一项无法使用，就得重新协调。

我想解决的不是「预约按钮太难点」，而是工程师已经知道要做什么测试，却仍需要反复拼凑设备、时间与审批流程。实验室搭建是我理解业务的起点，资源协调才是这个产品重点解决的问题。

原来的工作方式

  • 先根据测试任务自行判断需要哪些设备
  • 分别查找台架、示波器、电源的可用时间
  • 再核对设备状态、校准、使用资质等条件
  • 跨部门借用设备时等待管理员审批；冲突时重新协调
  • 预约后还要自己追踪审批和变更

希望得到的体验

  • 用一句话描述测试任务和时间需求
  • 系统给出设备组合与可用时段建议
  • 提前说明不可预约的原因与替代方案
  • 用户确认后才真正提交，重要规则由后端校验
  • 预约、审批、修改、取消都能查询和追溯
02

我的方案：让 Agent 做协调，让规则引擎做判断

从原有预约流程出发，我把产品方案拆成三个部分：需求表达、规则校验与预约执行，而不是简单增加一个聊天窗口。

01

先理解任务，再推荐资源

工程师说「想做 PMIC 纹波和启动时序测试」，系统需要帮助整理用途、时间和候选设备，而不只是搜索一个设备名称。建议是候选方案，不等于自动获得预约权限。

产品思考：把用户的测试目标转化为可执行的资源需求，减少反复查找和沟通。
02

关键规则交给确定性工具

设备占用、校准有效期、使用资质、时段冲突、周配额和特殊设备审批都应由后端查询和校验。对于不可预约的情况，系统应解释原因，并支持修改时段或更换同类型设备。

产品思考：AI 可以辅助理解和编排，但不能凭语言生成的结果绕过安全与业务约束。
03

提交前确认，提交后可追踪

从单设备预约扩展到多设备、多时段的确认单；对需要人工审批的申请展示原因；支持修改、取消和查看操作时间线。把用户真正关心的「到底约上没有」放在流程中心。

当前边界：已实现规则驱动的演示流程与 Agent 工具接口；尚未配置大模型 API，不能宣称具备完整的 LLM 自主规划能力。
03

从 MVP 到可用流程：我如何一步步迭代

我负责从业务场景出发梳理需求、设计流程，借助 AI 编程工具实现原型，并通过实际操作验收推动修复。我逐渐发现，「功能能跑」和「用户真正能用」是两回事。

1

先做基础预约：验证业务闭环

搭建资源列表、时段选择、预约记录等基础功能，让实验室资源从分散信息变成可查询的系统。

2

补上权限、资质、审批和规则

发现「空闲」不等于「能约」：设备校准、人员资质、配额、特殊设备与夜间申请都需要明确的判定逻辑。

3

让 Agent 辅助完成多设备预约

围绕 PMIC 测试等场景，尝试由需求描述生成资源建议，再通过确认单和后端工具完成预约；对缺少的信息要求用户确认。

4

从手动验收中发现新问题

我发现设备时段只能逐个预约、修改入口不完整，于是加入多时段选择、统一确认、预约修改和状态时间线。

5

自动化测试通过，浏览器却报 Not Found

实际验收发现修改与多时段提交失败。排查后发现服务仍加载旧路由；更新运行服务后重新验证成功。这让我意识到，自动化测试通过仍需真实用户路径验收。

05

它能带来什么价值？我会如何验证

目前使用的是 Mock 演示数据，没有真实上线或用户行为数据。以下是产品假设与未来验证指标，不是已经实现的业务提升结果。

工程师效率

减少寻找与协调设备的时间

衡量从提出测试需求到获得可执行预约方案的耗时，以及每次任务需要的人工沟通次数。

预约质量

降低冲突与无效提交

观察提交前规则拦截的原因、改期次数、预约失败率与人工介入比例。

流程透明度

让审批和变更有据可查

观察审批处理时长、状态查询次数，以及用户能否快速理解驳回或修改原因。

06

项目边界与下一步思考

这一版的重点是证明：真实业务问题可以被拆成明确规则、可调用工具和可验证的交互流程。 我把未完成的能力也清楚标出来。

当前已实现

规则驱动的预约演示闭环

资源查询、规则校验、预约与审批、多时段提交、修改取消、状态追踪，以及面向 Agent 的业务工具接口。

待验证

接入大模型后的需求理解与多步规划

需要评估模型对含糊需求、缺失参数、工具调用错误和不确定信息的处理效果，而不是只看能否生成一段自然语言回复。

真实落地前

连接真实设备数据与用户验证

当前设备、审批和配额均为模拟场景；还需要真实实验室系统对接、权限与安全评估，以及工程师和管理员的可用性测试。
