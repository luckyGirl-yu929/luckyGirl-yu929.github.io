03 / BUSINESS PROBLEM

难点不在「筛商品」，
而在把经验说清楚。

  • 经验分散选品规则依赖个人经验，难以沉淀和复用。
  • 规则复杂营销目标、类目经验和国家履约要求相互影响，配置容易遗漏。
  • 效率低人工反复筛选、核对和调整，难以快速完成大促商品池配置。
原有方式

口头需求 → 查找经验 → 手动配置条件 → 反复筛选 → 人工核对

Agent 辅助方式

需求结构化 → 知识检索 → 规则组装 → 人工确认 → 商品池交付

05 / KNOWLEDGE DESIGN

四层知识库设计

每层回答一个业务问题，
完整规则点击展开查看。

01

指标与标签知识

解决的问题：选品指标如何定义、如何比较？

典型示例：「低价」按类目相对口径比较，不用同一价格线筛所有类目。

展开完整说明

记录指标 ID、字段来源、统计窗口、运算符、阈值及有效期。

02

业务语言与指标映射

解决的问题：运营的模糊表达对应哪些标准指标？

典型示例：「万圣节」先用于扩展检索，不直接凭联想生成硬筛选条件；「爆品」需结合销量、增长、转化等指标取舍。

展开完整说明

不是只看销量；结合业务目标，从销量、增长、转化、库存等候选中做取舍。业务表达不能直接转成硬条件，避免 Agent 自造规则。

03

场景策略模板

解决的问题：某个选品场景从哪组规则开始配置？

典型示例：案例 A 的规则来源标识为 TPL_US_HALLOWEEN_HOME_CTR_v1.1，演示脚本按该模板组装国家、主题与履约条件。

展开完整说明

提供国家、活动、类目与楼层对应的初始策略；标出可调整顺序、不可放宽项和待确认参数。模板是起点，需结合当前供给重新预估。

04

历史选品 Case

解决的问题：以前的规则怎么改、为什么改？

典型示例：复用旧阈值前先检查适用场景、标签版本与当前商品供给，避免照搬。

展开完整说明

记录规则、运营修改、筛选漏斗与后续结果。复用前检查适用场景、标签版本、有效期和当前商品供给。

四层知识为方案设计。公开演示的模板、历史案例与冲突规则索引为空，尚未完成自动检索的全链路验证；演示结果由预设脚本复跑，不代表知识库已自动检索生效。

07 / EVALUATION & ITERATION

Agent 评测与迭代

过程、结果、业务价值分开评估，
每次优化都有明确的验证对象。

01

过程评测

需求解析是否准确、知识检索是否相关、规则参数是否正确。

02

结果评测

商品是否满足硬性条件、筛选结果是否符合选品目标。

03

业务价值

选品准确率、人工投入、重复筛选与返工情况。

BADCASE → FIX → REGRESSION

把「选得不准」拆成可修复的问题

基于 400+ 条 Agent 评测样本，按 Badcase → Fix → Regression 循环迭代；以下为整理资料中的代表性归因示例，用于说明评测方法。

目的国约束遗漏

问题表现
不符合目的国要求的商品入池。
原因分析
可运达国家等共享约束未前置。
优化方案
设为不可放宽的基础约束，并在执行前校验。
回归验证
不可运达商品被正确排除。

跨类目错误沿用低价阈值

问题表现
所有类目沿用同一低价线。
原因分析
指标口径未按类目区分。
优化方案
指标知识卡改用类目相对口径。
回归验证
跨类目与边界样本均验证通过。

节日主题被错误转成硬筛选条件

问题表现
把「返校季」限定成黑色。
原因分析
泛化联想被当成硬条件。
优化方案
主题词先用于扩展检索，硬条件必须有知识依据。
回归验证
无依据的颜色限制不再出现。

「爆品」规则组装不完整

问题表现
只保留销量条件。
原因分析
业务语言映射缺少必选指标。
优化方案
按映射核对增长、转化等指标。
回归验证
缺关键条件的反例被排除。
08 / REFLECTION

项目复盘

  1. 01

    Agent 不应该只是把自然语言转换成工具调用，而应理解业务目标、识别约束，并给出有依据的结果。

  2. 02

    对涉及业务决策的关键规则，应明确人机协作边界，保留人工确认。

  3. 03

    AI 产品的优化不能只依赖主观体验，需要建立评测集，通过 Badcase 持续验证和迭代。
